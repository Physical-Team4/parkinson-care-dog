# Raspberry Pi ↔ MechDog ESP32 USB 시리얼 통신 검증

- 시험일: 2026-11-26
- 시험·결과 제공: B 담당자
- 목적: 실제 Raspberry Pi 5와 MechDog ESP32 사이의 USB 시리얼 송수신 가능 여부 확인
- 기록 근거: B 담당자가 제공한 시험 조건, 관찰 결과, 집계 수치 및 일부 개별 로그
- 문서 작성 기준: `origin/main`의 `3e78f2c`
- 변경 범위: 검증 기록만 추가. 문서 작성 과정에서 하드웨어 시험·포트 열기·펌웨어 업로드를 재실행하지 않았다.

**결론:** USB 장치 인식, ESP32 로그 수신, MicroPython REPL을 통한 양방향 요청·응답,
REPL 내부의 임시 JSON·ACK 처리를 확인했다. 반복 시험은 20회 모두 성공했다.
이는 실제 팀 ESP32 통신 모듈의 적용 완료 또는 하트비트 업무 로직 검증을 뜻하지 않는다.

## 1. 시험 환경

| 항목 | 시험 당시 조건 |
|---|---|
| Raspberry Pi | Raspberry Pi 5 8GB |
| OS | Debian 13.7 Trixie |
| 아키텍처 | aarch64 |
| Python 환경 | Conda `pd-dog` |
| Python 버전 | 3.13.18 |
| Pi 시리얼 라이브러리 | pySerial (정확한 패키지 버전 미제공) |
| 상대 장치 | Hiwonder MechDog Advanced Kit 내장 ESP32 |
| 물리 연결 | Pi USB-A ↔ MechDog USB-C, USB 데이터 케이블 |
| USB 시리얼 칩 | CH340 |
| VID:PID | `1a86:7523` |
| 시험 당시 장치 경로 | `/dev/ttyUSB0` |
| 통신 설정 | 115200 Baud, 8 data bits, parity 없음, 1 stop bit (8N1) |
| 제어선 설정 | `DTR=False`, `RTS=False` |

장치 경로는 연결 순서에 따라 바뀔 수 있다. 위 경로는 이번 시험에서 확인한 값이다.
시험용 Pi 스크립트 전문, ESP32에 전달한 REPL 명령 전체, 전체 원본 로그는 제공되지 않았다.
이 문서에 없는 실행 명령이나 수치를 임의로 복원하지 않는다.

## 2. TEST 0 — USB 인식과 접근 권한

### 방법

MechDog 전원 OFF/ON에 따른 USB 장치와 시리얼 포트 인식 여부를 비교하고,
사용자 권한 및 시험 시작 전 포트 점유 상태를 확인했다.

### 결과

| 확인 항목 | 결과 |
|---|---|
| MechDog 전원 OFF | CH340 및 `/dev/ttyUSB0` 미인식 |
| MechDog 전원 ON | CH340 및 `/dev/ttyUSB0` 정상 인식 |
| 사용자 그룹 | `dialout` 권한 확인 |
| 장치 접근 | 읽기·쓰기 권한 정상 |
| 포트 점유 | 시험 시작 전 점유 프로세스 없음 |

전원에 따른 인식 차이는 이번 장비·연결 조건에서의 관찰이다.
다른 장치 또는 다른 전원 구성에서도 같은 결과가 난다고 일반화하지 않는다.

## 3. TEST 1 — ESP32 → Pi 수신

### 방법

시리얼 포트를 열고, 별도 명령을 전송하지 않은 채 5초 동안 수신한 뒤 연결을 종료했다.

### 결과

| 항목 | 결과 |
|---|---|
| 수신 시간 | 5초 |
| 총 수신량 | 387바이트 |
| 확인한 내용 | ESP32 부팅 로그 및 QMI8658 초기화 로그 |
| 포트 열기·수신·종료 | 성공 |

### 특이사항: 포트 열기 시 재부팅·초기 자세 동작

`DTR=False`, `RTS=False` 설정에도 포트를 열 때 ESP32 재부팅 로그와 로봇의 초기 자세 동작이 관찰됐다.
**정확한 원인은 미확인**이다. 제어선의 실제 전이, USB 시리얼 회로, 전원 상태 또는
기존 프로그램 중 무엇이 원인인지 이번 결과만으로 확정하지 않는다.

이 설정으로 리셋을 완전히 방지했다고 기록할 수 없다.
시험에서 보행·레이저 명령을 보내지는 않았으나, 관찰된 초기 자세 동작 때문에
‘로봇의 물리적 움직임이 전혀 없었다’고 표현하지 않는다.

## 4. TEST 2 — REPL 기반 양방향 송수신

### 방법

1. Pi에서 Ctrl+C를 전송해 ESP32의 기존 실행 프로그램을 일시 중단했다.
2. MicroPython REPL에 다음 Python 명령을 전송했다.

```python
print(123456 + 1)
```

3. Pi에서 ESP32의 반환값을 확인했다.

```text
123457
```

### 결과와 범위

- Pi → ESP32 명령 전달 성공.
- ESP32 → Pi 계산 결과 반환 성공.
- 같은 USB 시리얼 경로를 통한 양방향 요청·응답 가능 여부 확인.
- 기존 프로그램은 일시 중단했으며, 보드 파일을 수정한 것은 아니다.

Ctrl+C는 이번 REPL 시험에서 실행 상태를 바꾸기 위해 사용한 제어 동작이다.
이를 운영용 애플리케이션 메시지에 넣는 방식으로 사용하지 않는다.

## 5. TEST 3 — REPL 내부의 임시 JSON·ACK 처리

### 입력·응답

시험에서 사용한 JSON 내용:

```json
{"t":"hb","id":101}
```

ESP32에서 생성해 Pi가 확인한 응답:

```json
{"t":"ack","id":101,"ok":true}
```

### 결과

- ESP32 `ujson` 파싱 성공.
- 메시지 ID 추출 및 ACK 생성 성공.
- Pi 측 JSON 해석 및 요청·응답 ID 매칭 성공.

**중요한 제한:** 위 JSON은 REPL 명령 내부에서 임시로 처리했다.
일반 JSON 프레임을 실행 중인 팀 `SerialCommands` 모듈에 보내 처리한 시험이 아니다.
실제 REPL 래퍼 명령 전문은 제공되지 않았으므로, 위 JSON 예시를 당시 전송한 REPL 명령 전체로 해석하지 않는다.
`t="hb"`를 사용했지만 운영용 하트비트 감시·장애 판단 로직을 검증한 것은 아니다.

## 6. TEST 4 — 20회 반복 및 응답 시간

### 시험 조건

- 동일 시리얼 연결에서 REPL 기반 JSON·ACK 처리 20회 반복.
- ID 1~20을 순차 사용.
- 응답 제한 시간: 2초.
- 메시지 간 대기: 0.2초.
- 측정 구간: 송신 직전부터 일치하는 ID의 ACK를 수신할 때까지.

### 전체 결과

| 항목 | 결과 |
|---|---:|
| 시험 횟수 | 20회 |
| 성공 | 20회 |
| 실패 | 0회 |
| 성공률 | 100% (이번 20회에 한정) |
| 최소 응답 시간 | 29.80ms |
| 평균 응답 시간 | 40.38ms |
| 최대 응답 시간 | 87.05ms |

### 제공된 개별 로그

| ID | 응답 시간 |
|---|---:|
| 15 | 30.94ms |
| 16 | 39.27ms |
| 17 | 54.56ms |
| 18 | 35.94ms |
| 19 | 87.05ms |
| 20 | 31.84ms |

ID 1~14의 개별 응답 시간은 제공되지 않았다.
전체 통계는 제공된 20회 집계 결과를 기록한 것이며, 위 6개 값만으로 재계산한 통계가 아니다.
누락된 개별값·추가 분포 통계는 생성하지 않는다.

측정값은 REPL 명령 실행, JSON 처리, Pi 측 수신·해석을 포함한 왕복 응답 시간이다.
순수 UART 전송 지연이나 실제 팀 통신 모듈의 성능으로 해석하지 않는다.
20회 단기 시험 결과만으로 장시간 안정성 또는 운영 환경의 성공률을 보장하지 않는다.

## 7. TEST 5 — 제조사 프로그램 복구 확인

### 수행 절차

1. 시리얼 연결 종료.
2. USB 케이블 분리.
3. MechDog 전원 OFF/ON.
4. 기존 제조사 프로그램 및 기본 제어 기능의 정상 작동 확인.

결과는 **사용자 확인**이며 별도의 상세 로그는 제공되지 않았다.
파일을 다시 업로드하거나 펌웨어를 재설치한 복구가 아니라,
REPL 시험 후 전원을 다시 켜 기존 프로그램이 작동하는지 확인한 절차다.

## 8. 팀 프로토콜과 비교

비교 기준은 [USB 시리얼 프로토콜 초안 v0](../serial-protocol.md)다.
이 문서는 시험 결과를 기록하며 해당 프로토콜을 확정하거나 변경하지 않는다.

| 항목 | 이번 시험에서 확인한 범위 | 아직 확인하지 않은 범위 |
|---|---|---|
| 물리 연결·통신 설정 | 실제 USB 시리얼, CH340, 115200 8N1 사용 | 다른 장비·케이블·연결 순서에서의 동작 |
| JSON·ID·ACK | REPL 내부의 임시 파싱·생성, Pi의 ID 매칭 | 실제 `SerialCommands` 모듈의 프레임 처리 |
| 메시지 수신 | 부팅 로그 수신 및 요청별 응답 확인 | 최대 256바이트·UTF-8 경계·분할 수신·디버그 줄 필터 처리 |
| 응답 시간 | REPL 경로에서 제한 시간 2초 안에 20회 성공 | 의도적으로 응답이 없거나 지연되는 경우의 처리 |
| 하트비트 | `hb` 내용을 사용한 임시 요청·ACK | 1초 주기 송신·5초 무응답 판단 등 업무 로직 |
| DTR/RTS | False 설정에도 포트 열기 시 재부팅 로그·초기 자세 관찰 | 원인, 재현 조건 및 리셋 방지 방법 |
| 연결 복구 | 종료·전원 재인가 후 제조사 기본 기능 확인 | 운영 중 자동 재연결·안전 정지 정책 |

## 9. 변경하지 않은 항목과 한계

- 실제 팀 ESP32 통신 모듈을 업로드하지 않았다.
- 제조사 펌웨어 및 내부 파일을 수정하지 않았다.
- 실제 보행·레이저 명령은 전송하지 않았다. 포트 열기 시 관찰된 초기 자세 동작은 3절에 별도 기록했다.
- 실제 `SerialCommands` 및 하트비트 업무 로직은 미검증이다.
- 관찰된 재부팅 로그의 전체 원문, 387바이트 전체 수신 내용, 시험 스크립트 전문은 미제공이다.
- 문서 작성 과정에서 하드웨어 시험, SSH 접속, 포트 열기, 제조사 프로그램 실행을 재수행하지 않았다.

## 10. B·D 협의 및 후속 검증 항목

1. 포트 열기 시 ESP32 재부팅·초기 자세 동작의 원인과 방지 방법.
2. 실제 팀 통신 모듈을 이용한 JSON 프레임·ID·ACK 통합 검증.
3. 응답 시간 초과, 중복 요청, 단절·재연결 시 처리 정책.
4. 통신 장애 발생 시 안전 정지 및 알림 동작의 합의.
5. 운영용 하트비트 주기·장애 판정과 실제 프로토콜의 최종 합의.
6. 장시간 반복 및 장애 조건을 포함한 안정성 시험.

위 항목은 계획 또는 미검증 항목이며 완료 결과가 아니다.
후속 시험은 이번 기록과 구분하여 결과와 실행 조건을 남긴다.
